# 06 — Русский фронтенд и критические спаны

Единственный компонент, который переносится из Track A **без переделки** и при
этом остаётся источником научной новизны. Ни одна зарубежная модель русского
фронтенда не имеет.

## Текущее состояние

| Модуль | Что делает | Готовность |
|--------|-----------|-----------|
| `frontend/normalize.py` | NFC, аббревиатуры, пробелы; отдельная нормализация под ASR | рабочее |
| `frontend/verbalize.py` | Числа, даты, деньги в устную форму | рабочее, покрытие неполное |
| `frontend/stress.py` | Ударение комбинирующим акутом U+0301 | рабочее |
| `frontend/g2p.py` | Фонемизация | рабочее, в Track A не используется |
| `frontend/phone_vocab.py` | Словарь юнитов | привязан к Track A |

Порядок обработки зафиксирован: **TN → вербализация → ударение → (G2P)**.

## Известные дефекты, которые надо устранить

### Д1. Пунктуация выбрасывается

В `src/minispeech/data/forced_align.py`, функция `transcript_for_ctc` (~строка 776):

```python
plain = strip_stress(stressed).lower()
# Keep letters / digits / whitespace; drop punctuation (CTC alphabets are tight).
cleaned_chars: list[str] = []
```

Фильтр `_filter_ctc_chars_keep_stress` оставляет только `isalpha`, `isdigit` и
дефис. Запятые и точки не доходят до модели.

Причина исторически уважительная: выравнивание идёт через wav2vec2-CTC, в
алфавите которого пунктуации нет. Но следствие тяжёлое — модель не знает границ
синтагм, отсюда ровный ритм Track A.

В Track N ограничение снимается: LLM-бэкбон получает **обычный текст со всей
пунктуацией**, а CTC-выравнивание нужно только для псевдоразметки корпусов, не
для входа модели. Дефект исчезает архитектурно.

### Д2. Латиница попадает в `<unk>` — **устранён**

**Статус: закрыт в P0**, подтверждено измерением и на слух. Транслитерация и
вербализация латиницы работают до токенизации: `TTS-модель` даёт
`тэ-тэ-э́с-модель` (59 юнитов вместо прежних 54 с `t t s -`), набор `latin` из
117 позиций собран и измерен — median CER 0.106, CI95 [0.096, 0.171] на
подвыборке 50 (`out/baseline_m_critical.json`). Это первый случай в проекте,
когда изменение фронтенда дало слышимый эффект без переобучения модели.

Описание дефекта сохраняется как обоснование решения.

Фильтр пропускал латинские буквы (`ch.isalpha()` истинно для `a`–`z`), но
словарь юнитов построен на русском корпусе. На инференсе `PhoneVocab.encode`
не находит их и отдаёт `unk_id = 1`. «TTS» превращается в три одинаковых
unk-эмбеддинга.

Решение — транслитерация и вербализация латиницы на этапе TN, до токенизации:

| Вход | Ожидаемый выход |
|------|-----------------|
| `TTS` | `тэ-тэ-э́с` |
| `HR` | `эйч-а́р` |
| `Google` | `гугл` |
| `IT` | `ай-ти́` |
| `SMS` | `эс-эм-э́с` |

Нужны три механизма: словарь устоявшихся заимствований, правила чтения
латинских акронимов по буквам с русскими названиями букв, и **обязательный
fallback**, чтобы неизвестный символ никогда не доходил до `<unk>`.

Настоящая мультиязычность (общий фонемный инвентарь) потребовала бы английских
данных в корпусе, которых нет. Для нашей задачи транслитерация — не костыль, а
правильный ответ: русский диктор произносит английские аббревиатуры по-русски.

### Д3. Покрытие вербализации неполное

Набор `bank_entity` расширен до **315 позиций** (v1), но аудит M01 показал, что
46 % отвергнутых спанов — артефакты самой разметки, а не ошибки синтеза. То есть
дефект сместился: покрытие выросло, а корректность эталонных форм
`expected_spoken` не проверена. Нужны систематическое покрытие категорий из
таблицы ниже, тесты на каждую категорию и выпуск версии v2 —
см. [08_evaluation.md](08_evaluation.md).

## Н1: ударение как канал обусловливания

Гипотеза из [03_architecture.md](03_architecture.md), реализуется здесь.

**Проблема.** Передача ударения строкой с U+0301 хрупка: произвольный BPE
разорвёт ударный гласный на несколько токенов и потеряет связь метки с буквой.
См. [05_backbone.md](05_backbone.md).

**Решение.** Параллельно последовательности текстовых токенов идёт канал
признаков:

| Признак | Значения | Источник |
|---------|----------|----------|
| Ударение | позиция ударного гласного в токене / нет | `frontend/stress.py` |
| Омограф | флаг + выбранный вариант | словарь омографов + контекст |
| Граница синтагмы | нет / запятая / конец предложения / вопрос | пунктуация |
| Критический спан | нет / число / деньги / дата / реквизит / сущность | разметка TN |

Канал проецируется в размерность бэкбона и складывается с эмбеддингами токенов
либо подаётся как дополнительные позиционные признаки. Точная форма —
предмет абляции.

**Почему это новизна.** У VibeVoice такого канала нет; для английского и
китайского он не требуется. Для русского ударение различает лексемы, а не только
звучание. Это не инженерная деталь, а языково-специфичное архитектурное решение.

**Как проверяется.** Точность реализации ударения на расширенном наборе
`homograph` против варианта без канала. Гейт — [08_evaluation.md](08_evaluation.md).

## Разрешение омографов

Текущий `accentuate` работает на словаре и модели ударений. Омографы, различимые
только по контексту, словарь не берёт.

Уровни решения, от дешёвого к дорогому:

1. **Словарь + правила** — покрывает частотные пары, ошибается на контекстных.
2. **Классификатор на контексте** — небольшая модель поверх окна слов.
3. **LLM оффлайн** — Qwen или GigaChat разрешает омографы на этапе препроцессинга
   текста. Дорого на инференсе, но для батчевых сценариев приемлемо.
4. **Сам бэкбон** — если бэкбон уже понимает русский, он может разрешать
   омографы внутри, при условии что мы обучаем его на текстах с корректной
   разметкой ударений.

Вариант 4 наиболее элегантен и является дополнительным аргументом за
русскоязычный бэкбон. Требует корпуса с корректно расставленными ударениями —
это отдельная задача разметки.

## Н2: критические спаны

Ядро прикладного тезиса. Проектируется, реализации пока нет.

**Постановка.** В тексте выделяются фрагменты, ошибка в которых недопустима:
суммы, номера счетов и карт, даты, время, проценты, коды и идентификаторы,
названия организаций. Для остального текста допустима обычная генеративная
свобода.

**Компоненты механизма:**

1. **Разметка на входе.** TN уже знает, где число превратилось в слова —
   эту информацию надо не терять, а передавать дальше как признак спана.
2. **Обусловливание.** Признак спана идёт в канал из Н1; модель знает, что этот
   фрагмент требует точности, а не выразительности.
3. **Верификация на выходе.** Прогон синтезированного аудио через ASR и сверка
   именно критических спанов, а не среднего CER.
4. **Локальная регенерация.** При расхождении — повторная генерация **только
   отказавшего спана**, а не всей реплики. Механизм должен быть дешевле полного
   повторного синтеза, иначе он неприменим в телефонии.

**Открытый вопрос.** Как сшивать локально перегенерированный фрагмент без
слышимого шва. Возможные подходы: перегенерация с перекрытием и кросс-фейдом в
латентном пространстве, либо перегенерация всей просодической группы. Требует
эксперимента.

**Почему это новизна.** Генеративные TTS-архитектуры не дают гарантий на
содержание. Для intelligibility-critical применений это блокирующий дефект, и
механизм проверяемого синтеза — прямой ответ на него.
