# 10 — Вычисления и железо

> Все оценки в этом файле помечены `ОЦЕНКА` и подлежат уточнению по факту
> первых прогонов. Планировать по ним можно, обещать — нет.

## Текущее и целевое железо

| Ресурс | Сейчас | Целевое |
|--------|--------|---------|
| GPU | RTX 4080 / 4080 Super, 16 ГБ | RTX 6000 Pro, 96 ГБ |
| RAM | — | сотни ГБ |
| Диск | — | терабайты |
| CPU | — | десятки–сотни vCPU |
| Среда | WSL2 Ubuntu | та же, плюс возможность многокарточной конфигурации |

Ограничение по бюджету VRAM в Track A было ~14.5 ГБ при автоподборе батча.
Для Track N этот режим неприменим — нужен принципиально другой масштаб.

Вывод: **RTX 6000 Pro — минимум для реальной работы Track N**, и он же
недостаточен для финальных прогонов T3 и полной второй стадии. Это надо
закладывать в план: либо несколько карт, либо облачный бурст на финальные
обучения.

## Оценки стоимости обучения

`ОЦЕНКА` — порядки величин для планирования, не обязательства.

| Компонент | Параметры | Оценка на одной 96 ГБ карте |
|-----------|----------:|------------------------------|
| Акустический токенизатор, целевой | ~680M (энкодер + декодер) + дискриминаторы | недели |
| Семантический токенизатор | ~340M | ~половина от акустического |
| Diffusion-голова | ~40–123M | дни |
| Бэкбон 0.5B с нуля | ~0.5B | недели |
| Вторая стадия (LLM + голова) | зависит от бэкбона | недели |

### Единственный измеренный ориентир (M10)

`out/probe_lm_budget.json`, RTX 4080 SUPER 16 ГБ, синтетическая модель 0.517B,
bf16: **14 842 токена/с** при контексте 1024, микробатче 1, накоплении 8.
Экстраполяция при duty 0.70: 10B токенов ≈ 11 дней, 100B ≈ 111 дней.

Это **нижняя граница**. Пиковая занятость — 4.62 ГиБ из 16, activation
checkpointing включён, батч не подбирался. Число годится как «медленнее не
будет», но не как основание для календаря. Перед планированием предобучения
N-Lite замер повторяется при подобранном батче; требование зафиксировано в
[05_backbone.md](05_backbone.md).

Самая длинная цепочка: токенизатор → вторая стадия. Отсюда стратегия
де-рискинга из [04_tokenizers.md](04_tokenizers.md) — разрабатывать вторую
стадию на референсном токенизаторе параллельно с обучением своего.

## Что определяет стоимость сильнее всего

**Частота кадров.** Прямо влияет на длину последовательности и, следовательно,
на стоимость обучения и инференса LLM. Переход с 7.5 на 25 Гц удлиняет
последовательность более чем втрое. Это одна из причин, почему развилка Н3 —
не академический вопрос, а бюджетное решение.

**Curriculum по длине.** Референс идёт 4096 → 16384 → 32768 → 65536 токенов.
Нам такие длины не нужны: наш домен — короткие и средние реплики телефонии.
Ограничение потолка контекста заметно удешевляет вторую стадию.

**Размер бэкбона.** 0.5B против 10B MoE — разница на порядок и по обучению, и
по инференсу.

**Число шагов денойзинга.** Референс использует порядка 10 шагов. Прямо
торгуется против TTFB на инференсе; на обучение не влияет.

## Требования по латентности

Целевой сценарий — телефония. Ориентир из референса: VibeVoice-Realtime
достигает примерно 300 мс на бэкбоне 0.5B.

| Метрика | Цель | Гейт |
|---------|------|------|
| TTFB, тёплый старт | ≤ 300 мс | N8 |
| RTF | ≤ 0.3 | N8 |
| Холодный старт | измеряется отдельно | — |

Разложение TTFB измеряем покомпонентно, как уже делали в Track A
(`scripts/18_measure_ttfb.py`): фронтенд, бэкбон, первый латент, шаги диффузии,
первый чанк декодера. Без разложения непонятно, что оптимизировать.

Определение TTFB сохраняем прежнее: время от завершения нормализации текста до
первого буфера PCM длительностью не менее 20–40 мс.

## Инфраструктурные требования к коду

Закладывать до перехода на большое железо, иначе оно уйдёт на переписывание.

- **DDP-совместимость тренера.** Сейчас одно-GPU. На 96 ГБ сойдёт, на нескольких
  картах — нет.
- **Стриминговая загрузка данных.** Корпус не должен помещаться в память или на
  локальный диск целиком.
- **Чекпойнтинг с возобновлением.** Обучения на недели без устойчивого
  возобновления нежизнеспособны.
- **Градиентный чекпойнтинг и bf16.** Уже используется bf16 в Track A.
- **Отслеживание экспериментов.** `run_manifest.json` достаточен для десятков
  прогонов, но не для сотен.
- **Гигиена артефактов.** Веса, латенты и аудио не коммитятся — правило уже
  зафиксировано в `.cursor/rules/git-hygiene.mdc`; на тысячах часов дисциплина
  становится критичной.

## Правила окружения

Сохраняются из текущего проекта:

- GPU-работа выполняется в WSL, не в нативном Windows Python.
- Не запускать обучение из `/mnt/c/...`.
- Артефакты остаются в Linux FS; в Windows едут только числа через `docs/*.md`.
- Длинные задачи — в `tmux` с логом в файл прогона.
- Перед каждым GPU-прогоном: `git pull` и фиксация SHA в манифесте.
